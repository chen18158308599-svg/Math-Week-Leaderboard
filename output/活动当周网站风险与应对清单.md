# Math Week 活动当周网站风险与应对清单

适用活动：2026年10月19日至25日。检查日期：2026年10月17日。

依据：当前本地代码、已确认的操作规则、活动流程 PDF 和 Library Data Talk slides。**这是一份风险盘点，不代表已完成线上安全审计、压力测试或现场验收，也不能保证涵盖所有未知故障。** 本地功能存在，不等于已经部署或在线上完成数据库配置。

优先级：**P0＝正式计分前必须处理或明确停用；P1＝开场前核实并准备预案；P2＝活动中持续检查。** “已确认”表示代码或现有材料可直接确认；“待验证”表示尚不能确认线上或现场结果。

## 一、先看结论

1. **股票市场目前适合展示，不能直接当作正式个人资产比赛。** 现有页面明确使用本浏览器共享演示账户，资产保存在 localStorage，扫码登录尚未接入，且可模拟第一天结算。不能据此发正式奖项或承诺跨设备保存。
2. **目前不能严格保证所有领取者到过现场。** 隐藏题卡列表只减少入口；固定题卡链接、COM领取二维码和答案仍可被分享。需靠现场管理，或在正式计分前增加相应验证。
3. **必须验收“真实设备＋正式域名＋新学校账号”的完整流程。** 本地构建通过，不代表校园登录、网络、浏览器、二维码和数据库全部能配合工作。
4. **积分规则、截止时间和奖项要先统一。** 旧 PDF、旧二维码、后台分值和当前网站可能不一致，尤其是周六闭幕与周日活动结束的关系。
5. **准备故障登记和人工复核。** 出问题时先保留事实，不让多名委员各自随意补分、重置或修改数据库。

## 四、每天开馆前与闭馆后

**开馆前：**检查联网与展示授权 → 打开正式网站 → 核对日期和日程 → 用授权测试方式检查领取及排行榜 → 检查二维码、设备和委员值守。不要用正式参与者账号随意试领；测试数据如何排除要预先约定。

**闭馆后：**核对异常反馈与人工补分 → 保存必要的记录与榜单快照 → 处理停用活动或日程变动 → 退出管理员与委员账号 → 锁定展示设备。不要每天无差别清空正式积分。

## 五、故障发生时怎么处理

| 场景 | 当场动作 |
| --- | --- |
| 全站或登录不可用 | 暂停要求玩家重复扫码；公告故障；仍可继续不依赖网站的体验；登记待复核结果。 |
| 玩完无法领分或二维码超时 | 记录活动、玩家账号识别信息、结束时间和屏幕结果；由指定人员查 token 与提交记录后决定补分。不能默认每个口头申报都成立。 |
| 领取提示成功但总榜没更新 | 先查个人分数和后台提交，再考虑刷新延迟；不要立即再加一笔分。 |
| QR被公开传播或出现异常领取 | 暂停相关活动码并保留记录；调查范围；决定替换二维码、重新打印和争议处理，通知所有委员同步。 |
| 题卡正确答案被拒绝 | 记录原题、原输入、账号和错误提示；统一复核后修正，不当场向所有人公开标准答案。 |
| 股票市场出现资产丢失 | 当前演示数据不能当作正式资产恢复依据；若未来正式化，按服务器交易记录处理，不能凭本地截图随意重建。 |
| 准备恢复旧部署或改数据库 | 先记录当前版本和故障，确认备份及迁移兼容；由指定技术人员执行，避免多人同时改动。 |

建议故障记录字段：**时间、活动ID／名称、账号识别信息、发生设备、页面与提示、操作经过、截图、已有积分、处理人、处理结果**。不记录学校密码；领取链接视为敏感材料。

## 六、责任安排

- **技术负责人：**部署、数据库、登录、日志、回退和安全事件。
- **计分负责人：**规则解释、补分、撤销、申诉和最终榜复核。
- **内容负责人：**日程、地点、照片、网站与纸质信息同步。
- **现场负责人：**网络、设备、排队、委员培训和二维码保管。

同一人可以兼任，但每项必须有明确联系人和替补。**尚未解决的P0，应在开场前决定“修复后启用”或“暂不作为正式计分功能”，不能留给现场临时判断。**
